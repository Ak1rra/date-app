# Milestones 6–8 — Chat, feedback & notifications, hardening: design

Binding design for REQUIREMENTS §12.6–12.8. Tables from `v1-schema.md`.

## M6 Chat (AI-CHAT, AI-5, AI-SAFE-1..3)

- Threads: each member has one private thread (created on first use); the couple has one
  shared thread once a partner exists. `GET /chat/threads` → mine + shared.
  Access: private = owner only (404 otherwise); shared = both members.
- `GET /chat/threads/{id}/messages?before=&limit=50` → oldest→newest page.
  Messages with `hidden_for_user_id = me` are omitted.
- `POST /chat/threads/{id}/messages` `{content (1-2000)}` → **SSE stream**
  (`text/event-stream`): `event: delta {text}` chunks, `event: status {label}` for tool
  progress ("Finding places near you…"), `event: action {id, type, summary, payload}`
  for proposed write actions, `event: done {message_id}` and `event: error {code,
  message}`. The user message and the final assistant message are stored. Cap group
  `chat` (429 before streaming starts). CSRF applies (it is a POST).
- AI: smart tier, streaming (`messages.stream`, AI-5), adaptive thinking, the M2 tools
  (read-only) plus **proposal tools** that do not write: `propose_idea {idea fields}`,
  `propose_itinerary_change {itinerary_id, description, stops?}`,
  `propose_calendar_slot {starts_at, ends_at, idea_id?}`. Each becomes an `action`
  stored on the assistant message (`actions[]` with a uuid and `applied_at: null`).
  Context: the requester's `build_context` (their own notes only; surprises excluded for
  the surprisee) + the last 30 messages of the thread. In the shared thread, the
  context is built for the **sender** but `planner notes` are excluded (shared thread
  replies are seen by both, so private notes must not leak) and so is every surprise
  (both directions).
- `POST /chat/actions/{action_id}/apply` → applies via the normal services (create
  private idea, or shared idea when proposed in the shared thread; itinerary edit via the
  M3 stops service — planner only; calendar slot → `schedule` only if the requester is the
  planner of that itinerary, else it creates a draft from the idea). Idempotent
  (`applied_at` set once). The applier must be able to see the thread (no silent writes).
- Off-topic (AI-SAFE-1): the system prompt keeps it to date planning and politely
  redirects; caps protect cost.
- Frontend `/chat`: thread switcher (Mine / Together), streaming bubbles, tool-progress
  chips, action cards with Apply/Dismiss, author attribution in the shared thread using
  the husband/wife colours.

## M7 Feedback & notifications (FR-RATE-*, AI-6 taste, FR-NOTIF-*)

- Completion: job `itinerary.complete` at `ends_at` (dedupe per itinerary/ends_at) sets
  status `completed` and creates in-app rating prompts (notification kind
  `rate_prompt`) for both members (FR-RATE-1). Reschedule re-enqueues; stale jobs no-op.
- Ratings: `PUT /itineraries/{id}/rating {stars, would_again, comment?, stop_thumbs?}`
  (each member, only for completed itineraries visible to them; a surprise must be
  revealed — completion reveals any still-hidden surprise). `GET
  /itineraries/{id}/ratings` → mine always; the partner's only when both rated or 7 days
  after `ends_at` (FR-RATE-2); then publish `rating.revealed`.
- Planner's read: `PUT /itineraries/{id}/planner-read {enjoyment, highlights?, misses?}`
  planner only, never shown to the other member (FR-RATE-2a).
- `GET /past-dates` → completed itineraries with my rating, the partner's (if revealed),
  and (planner only) my planner read (FR-RATE-4).
- Taste summary (AI-6): job `taste.recompute` debounced (dedupe key per profile per
  10-minute bucket, run_at +2 min) after ratings, planner reads and votes. Builds counts
  in code (liked/passed categories, price levels, indoor/outdoor, would-again, stop
  thumbs, the recipient's own ratings weighted 2× the planner's read, FR-RATE-3) and asks
  the fast tier for a ≤ 120-word "what they enjoy" summary as structured output; stores
  `taste_summaries` and `build_context` includes it.
- Notifications: `services/notify.py` `notify(user_id, kind, title, body, data,
  dedupe_key=None, respect_quiet_hours=True)` inserts a row with `deliver_after`
  (quiet hours default 22:00–08:00 in the user's timezone push activity notifications to
  08:00, FR-NOTIF-3) and enqueues `push.send` at `deliver_after`. Per-kind toggles in
  `users.notification_settings` (`{"kinds": {kind: bool}, "quiet_start": "22:00",
  "quiet_end": "08:00"}`); `GET/PUT /me/notification-settings`.
- `GET /notifications?unread=` / `POST /notifications/{id}/read` / `POST
  /notifications/read-all` — in-app centre (only `deliver_after <= now()`).
- Web Push: `pywebpush` with VAPID keys from env (missing → in-app only);
  `POST /me/push-subscriptions {endpoint, keys:{p256dh, auth}}`, `DELETE
  /me/push-subscriptions?endpoint=`; job `push.send` sends to each subscription and
  deletes 404/410 endpoints. Payload is the notification title/body only. `dateapp vapid
  generate` CLI prints a key pair for `.env`.
- Kinds: `reminder_day_before` (18:00 local the day before: weather heads-up from a fresh
  forecast, what to bring, validation flags — re-validated at send time) and
  `reminder_hour_before` (FR-NOTIF-1), exempt from quiet hours only if the date starts in
  them; `checklist_due` (planner only, unticked items, at `due_at - 24 h`, FR-PLAN-6);
  partner activity (FR-NOTIF-2): `match`, `ideas_added` (batched: at most one per hour),
  `date_announced`, `date_rescheduled`, `date_cancelled`, `hint_released`,
  `surprise_revealed`, `partner_reaction`; `rate_prompt`. The M3/M4/M5 hooks
  (`on_scheduled`, hint/reveal, match) call `notify`. Surprise-related text is generic
  (FR-NOTIF-5): reminders for a surprise say "Your surprise date is in 1 hour! ✨" to the
  surprisee and never name a venue.
- Frontend: rating sheet (stars, would-again, comment, per-stop thumbs) from the prompt
  and on past dates; planner's read form ("How did she like it?"); past dates list;
  notification bell + centre; settings page for kinds + quiet hours; push opt-in with the
  iOS Home-Screen guide (FR-NOTIF-4, UX-8); the service worker shows push notifications
  and focuses/opens the app on click.

## M8 Hardening (NFR-*)

- Authorization sweep: one parametrized test module enumerating every route in the app
  (from `app.routes`) and asserting 401 without a session, 404 for another couple's ids,
  and the surprisee marker-string sweep from M4 over every GET (NFR-SEC-2).
- Account deletion + export (FR-AUTH-3, NFR-PRIV-2): `GET /me/export` → JSON of the
  user's own data (profile, notes they wrote, ideas they created, votes, ratings, planner
  reads, chat messages they authored, notifications); `DELETE /me` → marks deleted,
  revokes sessions, leaves the couple, and schedules `user.purge` at +30 days
  (immediately anonymises email/display name). In `NO_LOGIN` mode both are available
  from the Profile tab ("Delete this profile's data" resets that household profile).
- Privacy page `/privacy` (NFR-PRIV-3): which third parties receive what (Anthropic,
  Google Maps Platform, Ticketmaster, Open-Meteo, Resend) and the no-login trust note.
- Ops usage report (COST-4): `dateapp usage [--month YYYY-MM]` CLI prints per-couple
  runs, tokens and est. cost by feature, plus the global total vs the ceiling.
- Accessibility pass (UX-4): axe checks in component tests (`vitest-axe` or
  `jest-axe`-style via `axe-core`, dev dependency) for every page; keyboard paths for
  the deck and the itinerary editor; reduced motion.
- CSP stays strict; the WebSocket and SSE are same-origin (`connect-src 'self'`).
- e2e smoke (NFR-QA-1): Playwright, run on rogue against a throwaway DB with
  `DEMO_MODE=1 NO_LOGIN=1`: (a) solo planner path: pick Husband → setup → fill both
  profiles → plan (options) → itinerary → schedule as surprise → planner's read after
  completion (time travelled via a test-only job trigger); (b) match path: Husband
  generates ideas → swipes → switch to Wife → swipes → match → itinerary → schedule →
  both rate. `NO_LOGIN` replaces invite/join in the smoke because that is how the app is
  deployed; invite/join keep their API tests.
- README: run/test/check commands (NFR-QA-2), env vars; HUMAN.md.
