# Milestone 1 — Foundation: design

Binding design for Milestone 1 (REQUIREMENTS §12.1). Workers implement this;
deviations go back to the orchestrator as a `BRIEF CONFLICT`. Requirement IDs
refer to `REQUIREMENTS.md`.

## Scope

In: repo tooling, DB + Alembic, magic-link auth (FR-AUTH-1), sign out / sign out
all (FR-AUTH-3, partial), couple space created at sign-up (FR-PAIR-0),
couple-scoped authorization (FR-PAIR-4, NFR-SEC-2), both profiles incl. the
planner-maintained partner profile (FR-PROF-1..5, FR-PROF-7 data model),
planner notes + "ideas she's mentioned" (FR-PROF-8), Postgres job worker
(§14 decision 1), DEMO_MODE fakes for email + geocoding (INT-1, NFR-QA-3),
PWA shell with nav (UX-1/2/3/6, FR-PLAN-1 entry point), health + JSON logs
(NFR-REL-2), lint/type/test tooling (NFR-QA-2), native build/serve/deploy
tooling (NFR-QA-3).

Deferred: OAuth (FR-AUTH-2, SHOULD), account delete + export (FR-AUTH-3 delete,
NFR-PRIV-2 → M8), invite/join + profile hand-over UI (FR-PAIR-1..3, FR-PROF-7
hand-over → M5), playful quiz onboarding (FR-PROF-6 SHOULD; M1 ships a short
3-step setup instead), real Google geocoding (pending INT-2 ToS research → M2).

## Conventions

- **IDs** UUID v4 generated in Python. **Times** `timestamptz`, UTC, timezone-aware
  `datetime` everywhere (FR-CAL-6). Display conversion is the client's job.
- **Errors** — every non-2xx JSON body is `{"error": {"code": str, "message": str}}`.
  `ApiError(status, code, message)` is raised in services; FastAPI validation
  errors map to `422 {"error":{"code":"validation_error","message":..., "fields":[...]}}`.
- **Authorization** — couple-owned rows are always queried with
  `WHERE couple_id = :member_couple_id`; an id from another couple is a **404
  `not_found`** (never 403, so existence doesn't leak). Author-only rows (planner
  notes) add `author_user_id = :me`, also 404 otherwise. Edit rights that the
  viewer *can* see but not change (the joined partner's profile) are **403
  `forbidden`**.
- **Lists in profiles** are JSONB arrays of enum strings, validated by Pydantic.

Deviation from §8, deliberate: **availability hangs off `partner_profiles`, not
`user_id`**, because the planner fills in the partner's availability before she
has a user (FR-PROF-7). Planner notes point at `about_profile_id` for the same
reason (§8's nullable `about_user_id`).

Enums: categories = `food, outdoors, arts, music, sports, games, learning,
nightlife, wellness, travel, shopping, nature, culture, adventure, relaxing`;
transport = `car, transit, walk, rideshare, bike`; dietary = `vegetarian, vegan,
pescatarian, gluten_free, dairy_free, halal, kosher, nut_free, low_carb`.
Profile category and dietary lists contain at most 30 items. Cuisines and allergies
are free-text strings of 1–40 characters, with at most 30 items per list.

the 0001 schema.

## Sign-up and the couple space (FR-PAIR-0)

A first successful verify for a new email, in **one transaction**, creates: the
user; a couple (`status=active`, `timezone` from the verify request's optional
`timezone`, else UTC); `couple_members(role=owner)`; two `partner_profiles`
(`owner` slot with `subject_user_id = user`, `partner` slot with
`subject_user_id = null`); an empty `couple_constraints` row.

## Auth (FR-AUTH-1, FR-AUTH-3, NFR-SEC-1)

- **Tokens**: `secrets.token_urlsafe(32)`; DB stores `sha256` hex only.
- **Magic link**: `POST /auth/magic-link {email}` → always `202 {"ok": true}`
  (no account enumeration). Link = `{APP_ORIGIN}/auth/verify#token=<token>`:
  the token is in the **fragment**, so it never reaches server logs or a
  Referer. TTL 15 min, single-use.
- **Verify**: `POST /auth/verify {token, timezone?}` → on success marks the token
  used (`UPDATE … WHERE used_at IS NULL AND expires_at > now() RETURNING`, so
  two concurrent verifies cannot both win), creates the user + couple if new,
  creates a session, sets cookies, returns `200 SessionOut`. Any failure →
  `400 invalid_token` with one generic message.
- **Session cookie** `session`: HttpOnly, SameSite=Lax, Secure=`COOKIE_SECURE`,
  Path=/, Max-Age = 30 d. Server-side `sessions` row; `last_seen_at` updated at
  most once per 5 min. Logout revokes the row; logout-all revokes all the
  user's rows.
- **CSRF** (double submit): cookie `csrf_token` (not HttpOnly, SameSite=Lax,
  Secure per config) set by middleware on any response that lacks it and
  rotated at login; every `POST/PUT/PATCH/DELETE` under `/api/v1` must send
  header `X-CSRF-Token` equal to the cookie (`hmac.compare_digest`), else
  `403 csrf_failed`. This includes the unauthenticated auth endpoints.
- **Rate limits** (`429 rate_limited` + `Retry-After`): magic-link ≤5 per email
  per 15 min (counted in `magic_link_tokens`, so it survives restarts) and ≤20
  per IP per 15 min (in-process sliding window); verify ≤30 per IP per 15 min.
- **Headers** on API responses: `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`,
  `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`,
  `Cache-Control: no-store` on `/api/v1/auth/*` and `/api/v1/me`.
- **CORS**: only `APP_ORIGIN`, credentials allowed. In the Vite dev server the
  web app and API share an origin via the proxy.

With `NO_LOGIN=1`, email sign-in is disabled and the first screen is a Husband/Wife
picker. `POST /api/v1/auth/choose-profile` accepts only `husband` or `wife`, creates
the reserved household accounts on first use, opens a session, and replaces any
current session. Husband is the couple owner and Wife is the partner member; this
mode has no PIN or other protection, so anyone who can reach the app can switch
profiles. The Profile tab exposes the same switch after entry.

## API contract (`/api/v1`)

Unauthenticated: `GET /health` → `{"status":"ok","db":"ok"}` (503 with
`"db":"error"` if the DB ping fails); `GET /meta` → `{"demo_mode": bool,
"no_login": bool, "version": str}`; `GET /auth/session` →
`{"authenticated": bool, "user": MeOut|null}`; `POST /auth/magic-link` and
`POST /auth/verify` (404 while `NO_LOGIN=1`); `POST /auth/choose-profile`
(`{"profile":"husband"|"wife"}`) while `NO_LOGIN=1`; `GET /dev/outbox`
(DEMO_MODE only, else 404) → `[{"to","subject","link","sent_at"}]` newest first,
last 50, in memory.

Authenticated (else `401 unauthenticated`):

| Method + path | Body → response | Rule |
|---|---|---|
| `POST /auth/logout`, `POST /auth/logout-all` | → 204, clears cookies | |
| `GET /me` / `PATCH /me` | `{display_name?, timezone?}` → `MeOut {id, email, display_name, timezone, couple_id, role}` | timezone must be a valid IANA zone |
| `GET /couple` / `PATCH /couple` | `{name?, timezone?}` → `CoupleOut {id, name, timezone, status, home_area: {label, lat, lng}|null, members: [{user_id, display_name, role}], partner_joined}` | |
| `PUT /couple/home-area` | `{query}` → `HomeAreaOut` | geocodes, stores label + coords rounded to 2 dp + place id; `query` not stored; provider unavailable → `503 provider_unavailable` |
| `GET /couple/constraints` / `PUT` | full `ConstraintsIn` → `ConstraintsOut` | `budget_min <= budget_max` |
| `GET/POST /couple/important-dates`, `PATCH/DELETE /couple/important-dates/{id}` | `ImportantDateIn` → `ImportantDateOut` | `profile_id` must be in the couple |
| `GET /profiles` | → `[ProfileOut]` (both slots, owner first) | `ProfileOut` = all profile fields + `id, slot, is_me, subject_joined, can_edit, edited_by_user_id, confirmed_by_subject_at, updated_at` |
| `GET /profiles/{id}` / `PUT /profiles/{id}` | full `ProfileIn` → `ProfileOut` | **can_edit = subject_user_id is null OR subject_user_id = me**; else 403. Sets `edited_by_user_id = me` |
| `GET /profiles/{id}/availability` / `PUT` | `{windows: [{weekday,start_time,end_time}], blocks: [{date, note?}]}` replace-all | same edit rule as the profile |
| `GET /notes?kind=` / `POST /notes` | `{about_profile_id, kind, text}` → `NoteOut` | lists only `author_user_id = me`, non-archived; `about_profile_id` must be in the couple and not the author's own slot |
| `PATCH /notes/{id}` / `DELETE /notes/{id}` | `{text?, archived?}` | 404 unless author |

`backend/openapi.json` is generated by `uv run python -m app.openapi_export` and
committed; a test fails if it is stale. The frontend generates
`src/api/schema.d.ts` from it with `npm run gen:api`.

## Worker (§14 decision 1, NFR-REL-1)

`python -m app.worker`: loop every 2 s; claim ≤10 due jobs (`status='queued' AND
run_at <= now()`, or `status='running' AND locked_at < now() - 10 min`) with
`FOR UPDATE SKIP LOCKED`, set `running/locked_at/locked_by`, commit, run the
handler from a `kind → async handler(session, payload)` registry. Success →
`done`; exception → `attempts+1`, re-queue at `now + 30 s × 2^attempts` until
`max_attempts`, then `failed` with `last_error`. Unknown kind → `failed`.
`enqueue(session, kind, payload, run_at=None, dedupe_key=None)` uses `INSERT … ON
CONFLICT (dedupe_key) DO NOTHING`. Handlers must be idempotent. M1 ships one
periodic job, `auth.cleanup` (delete magic-link tokens expired >1 day, sessions
expired or revoked >7 days), self-scheduled hourly with dedupe key
`auth.cleanup:<YYYY-MM-DDTHH>`. SIGTERM finishes the current batch and exits.

## Deployment

The native production update is run on the Linux host from the repository:

```
ssh rogue@192.168.1.167
cd ~/projects/date-app
dateapp daemon update
```

`daemon update` refuses an uninstalled service, tracked uncommitted changes, or a
non-fast-forward pull. It then runs `git pull --ff-only`, a database backup,
dependency sync, the frontend build, `alembic upgrade head`, restarts `date-app`,
and waits up to 30 seconds for `/api/v1/health`.

## Providers (INT-1)

- `EmailSender` protocol: `async send(to, subject, text, html) -> None`.
  `ConsoleEmailSender` logs the message and appends to the in-memory dev outbox;
  `ResendEmailSender` posts to `https://api.resend.com/emails` with
  `Authorization: Bearer EMAIL_API_KEY` via httpx (timeout 10 s).
- `Geocoder` protocol: `async geocode(query) -> GeocodeResult(label, lat, lng,
  place_id | None)`. `FakeGeocoder` is deterministic: label =
  `"<Title Cased Query> (demo)"`, coords = a fixed demo centre (Austin, TX
  30.2672, -97.7431) plus an offset of up to ±0.05° derived from a hash of the
  query. No real geocoder in M1; without DEMO_MODE the endpoint returns
  `503 provider_unavailable`.
- `providers/registry.py` picks implementations from `Settings` and is a FastAPI
  dependency so tests can override it.

## Tests

pytest + pytest-asyncio, httpx `AsyncClient(ASGITransport(app))`, real
Postgres at `TEST_DATABASE_URL`. Session-scoped fixture drops and recreates the
`public` schema and runs `alembic upgrade head`; an autouse fixture truncates
all tables after each test. Helper `login(client, email) -> client` goes through
magic-link → dev outbox → verify, carrying the CSRF header. Fixture
`make_partner(couple)` inserts a second member directly (the join flow is M5)
so author-only and edit-rule tests have a partner.

## Frontend (UX-1..6, FR-PLAN-1, PWA)

- Routes: `/signin`, `/auth/verify` (reads `#token`, clears it with
  `history.replaceState` before posting), `/setup` (3 steps: your first name →
  partner's first name → home area + timezone from `Intl`), and the app shell:
  `/` Home, `/ideas`, `/calendar`, `/chat`, `/us`, `/profile`, `/plan` (placeholder).
  Signed-out users are redirected to `/signin`. After a no-login profile choice,
  the app loads the couple and opens `/setup` when it has no home area and this
  device has not set the local "skip setup" flag; otherwise it opens the requested
  destination. The setup name field is prefilled from the selected profile/session.
- Shell: bottom tab bar on mobile (Home, Ideas, Calendar, Chat, Us, Profile), top nav
  from `md` up. Home shows a large "Plan a date" button (FR-PLAN-1, links to
  `/plan`), and empty-state cards for next date / finishing touches / occasions.
  Ideas, Calendar, Chat are teaching empty states (UX-6); Ideas shows an
  invite-partner CTA in place of the deck (UX-2).
- Us: my profile, partner profile ("Here's what you know about {name}"),
  shared constraints, home area, important dates, availability (both), and
  "My notes about {name}" + "Ideas {name} mentioned" with an **"Only you can
  see this"** badge (FR-PROF-8, UX-7).
- Theme: CSS variables for a warm palette (blush/coral/peach + deep plum
  accent), light and dark via `prefers-color-scheme` (UX-3); motion wrapped in
  `motion-safe:` (UX-4). The husband (owner) selects the blue palette; the wife
  (partner) keeps the warm palette. `usePersonTheme` maps the role to
  `data-person`, including matching light/dark browser theme colours.
- API client: `openapi-fetch` typed by `schema.d.ts`, `credentials: 'include'`,
  middleware adds `X-CSRF-Token` from the `csrf_token` cookie on unsafe methods;
  calls `GET /auth/session` at boot so the cookie exists.
- PWA: `vite-plugin-pwa` (generateSW), manifest name "Date Planner", short
  name "Dates", theme colour from the palette, 192/512 + maskable PNG icons;
  `/api/*` is never cached by the service worker in M1.
